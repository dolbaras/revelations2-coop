# Revelations 2 co-op: the shared world (stage 6 and 6b)

Status: **on by default once a session starts** (stage 6i: `session_defaults()` switches the world module, scenario flag sync 1 and the co-op door replay 2 on at `START` / when joining a running game; `REV2_WORLD_DEFAULTS=0` or `net w defaults 0` keeps a lab run's own values; `REV2_WORLD=1` / `net w on` still start the hooks at the first frame for tests). Stage 6 (verified on two PCs, Episode 1, LAN and RTT 120 ms): enemy creation from host records by LayoutID, enemy position / HP / action mirrored (idle enemies), client hit -> host enemy (HIT, exact damage, 20 of 20 arrived),
replica follows the host's death through the records. Stage 6b adds the story layer (flags, scene starts, inventories, equipment, the game's own cutscene sync point, enemy deaths); the section "6b: what was seen on hardware" at the end says which parts ran live and which did not.
Source: `native/world.inc` (hooks, events, enemy records), `native/story.inc` (stage 6b), `native/probe.inc` (reverse-engineering probe), `native/coop_session.c` (`cs_send_world` / `cs_recv_world`), `native/coop_proto.c` (WORLD message). The wire format of the base protocol is in `protocol.md`.

## Principle

Mirror model with host authority per object. Both PCs run the engine and the story script (the scenario FSM); the host's enemies and items are the truth. A client creates a placed object only when the host announced it (its own creators are refused), drives it from host records,
and forwards what its human does to it (hits, pickups). The client's own body is driven by its input only.
Objects are identified by the engine's own placement id, the **LayoutID** embedded in every placed object: `i32 a` at `+0x19CC`, `u16 b` at `+0x19D0`, `u16 c` at `+0x19D2`.
Because both PCs run the story, a scripted effect (a weapon given to a character, a scene) happens on both PCs once its trigger fires on both; the layer shares the **triggers and the human's own actions**:
flags, what a human takes from the world, scene starts that only one PC's trigger produced, and the personal inventories of both slots.

## Messages

World events (reliable, relayed by the host; kinds `CP_EV_USER + n`, body little endian; the body is at most 96 bytes):

| Kind | Name | Direction | Body |
|---|---|---|---|
| 0x120 | SPAWN | host -> client | `i32 a, u16 b, u16 c, f32 pos[3], u32 hp` (24 bytes): create the enemy with this LayoutID |
| 0x121 | HIT | client -> host | `i32 a, u16 b, u16 c, i32 damage, u8 slot, u32 flags28, u32 flags2c` (21 bytes): apply the damage to the real enemy, attacker = the client's puppet |
| 0x122 | DEATH | host -> client | `i32 a, u16 b, u16 c, u8 killer slot (255 none), u32 action, u32 flags28, u32 flags2c` (21 bytes): the replica dies through ApplyDamage with the killer's DamageInfo (the killer's PC credits the kill: achievements, blow type flags of the killing hit) |
| 0x123 | PICKUP | any -> other | `u32 item, u32 count, i32 a, u16 b, u16 c, u8 slot` (17 bytes): the other PC puts the item into that slot's inventory through PutItem with its own copy of the object (found by LayoutID; no object here = already gone, skipped) |
| 0x125 | PDMG | host -> owner | `u8 slot, i32 amount` |
| 0x126 | FLAG | any -> other | `u32 id, u8 value`: the same story flag bit here (replay guard, no echo) |
| 0x127 | SCENE | any -> other | chunk of a sDemo request: `u8 submit index (0..2), u8 chunks, u8 chunk no, u8 scene id, bytes[<= 80]`; the receiver reassembles the request (200 bytes) and submits it unless it submitted the same bytes (hash) in the last 5 s |
| 0x128 | GRANT | any -> other | `u32 item, u32 count, u8 slot` (9 bytes): a story grant of a unique item: the other PC makes sure its copy of that slot holds the item (skipped when it does) |
| 0x129 | DOOR | any -> other | `i32 a, u16 b, u16 c, i32 action, i32 previous action` (16 bytes): a placed set model (door, locker, crate; sSetModel `0x1581920`) changed its action id (`+0x1A54`) on the sender, i.e. a human operated it; the other PC switches its copy to the same action through the set model's ChangeAction (vtable `+0xB8`) unless it is there already. The scan runs at 10 Hz on both PCs, first sightings and the first 4 s after a level load never send, an applied action is the new baseline (no echo). Co-op set models (the `uSmCoopBase` family: co-op doors, shutters) are not mirrored by default: their action dereferences its actor (a player) at once, a bare ChangeAction crashed the game. The research switch `net w doors coop 1` sends them as an 18-byte body (`+16` coop flag, `+17` the sender's slot) and the receiver writes the sender's puppet into the action's actor field (`+0x1A38+0xC`) before the ChangeAction; untested on a human at a shutter. Stage 10: the co-op body is 31 bytes (`+18` f32 position of the sender's object, `+30` its kind) so that a border shutter that is active here under its other stage's layout id is found (same kind within 150 units); push boxes and carried objects (`uSmMoveBox` family) are not mirrored by action any more (the push box's Press start calls the actor's virtual, a bare ChangeAction has none) except Break / Broken of a carried object: their transform goes by PROP; a co-op change whose actor (action instance `+0xC`) is the partner's puppet is this PC's replay and is not sent |
| 0x12A | BARRIER | any -> other | `u8 kind` (8): this PC reached the cutscene sync point |
| 0x12C | SF | any -> other | `i32 area, u16 index, u8 value` (7 bytes): a scenario flag of the area was set (sync 1) / changed (sync 2) on the sender. Stage 10: the index covers 0..511 (every flag of the current area; release-020 scanned 0..299), and `area` 99 means an EpisodeFlag (global flag `99000 + index`, getter `0x8681B0`); a flag of an area this PC is not in yet is kept up to 15 s |
| 0x12E | PROP | any -> other | stage 10: `i32 a, u16 b, u16 c, u8 flags (1 moving, 2 settling, 4 final rest), u8 sender slot, u16 seq, f32 pos[3], f32 quat[4], i32 action` (44 bytes): the transform of a movable set model (push box `uSmPress`, carried object `uSmInteractive`) whose current action's actor is the sender's human (a carried object only while it hangs on its holder: `+0x40` relative differs from the world `+0xE0`; the game keeps the carrier as the actor after the put-down); a held carried object sends its world position `+0xE0`; sent at most 10 times a second while it changes, for 2 s after the human let go, then once as the final rest. The receiver writes position `+0x40`, quaternion `+0x50`, root matrix translation `+0xE0` (and for a push box at rest `+0x4360` / `+0x4370`) unless its own human holds that object or the sample is older than the last one |
| 0x12F | SF digest | any -> other | stage 10: `i32 area, u8 kind (0 area flags, 1 EpisodeFlags with area 99), u8 word count (16), u32 words[16]` (70 bytes, the game's bit order: `0x80000000 >> (n & 31)` of word `n >> 5`): every flag set on the sender at the end of its quiet window after a load; the receiver sets those it misses (sets only); a digest of another area waits up to 15 s for this PC to enter it |
| 0x131 | INV | owner -> other | combat4: `u8 owner slot, u8 flags (1 begin of a full set, 2 end), u8 seq, u8 n, n x (u8 index, u16 id, i32 count, u32 +0x18)`: entries of the sender's own human; the receiver reconciles its copy of that slot (section "combat4") |
| 0x132 | INVREQ | any -> owner | combat4: `u8 sender slot`: send me a full set (every 2 s until the table is complete) |
| 0x133 | INVADJ | any -> owner | combat4: `u8 owner slot, u8 n, n x (u16 id, i32 delta, u32 +0x18)`: the sender's inventory screen moved items into / out of the owner's human (the hand-over) |
| 0x134 | THROW | thrower -> other | combat4: `u8 slot, u8 throw number (bomb; 0 from older peers), u16 item id, f32 vectors[4][3]`: the sender's human launched a projectile; the receiver creates the same uWpBomb for the puppet |
| 0x135 | BOOM | thrower -> other | bomb: `u8 slot, u8 throw number, u16 item id, f32 pos[3]` (16 bytes): the sender's bomb of that throw explodes at `pos` (its `+0xE0`); the receiver puts its copy there and starts the copy's explosion (action 8), for the eye only (section "bomb") |

`WORLD` (type 0x51, unreliable, sequenced like `STATE`; `u8 pid, u8 kind, u16 seq, u32 t_ms, u8 epoch, u16 len, body[<= 400]`): stale epochs and old sequence numbers are dropped, the host relays to other clients, the receiver polls a ring of the newest 64.
Kind 1 = enemy records, 32 bytes each: `i16 a, u16 b, u16 c, f32 pos[3], i16 yaw (rad*10000), i16 hp, u16 action, u16 previous action, u32 pstate (+0x37B8), u8 target slot (255 none), u8 reserved`, sent by the host at about 15 Hz for every live enemy; the client moves the replica with the engine's remote-control fields
(`+0x39A0` target position, `+0x39C4` yaw, `FUN_00ADCA10` / `FUN_00ADC8C0`), sets the HP when the host's is lower (a host HP of 0 waits up to 1.5 s for the DEATH event, which kills through ApplyDamage), and switches its action with `ChangeAction` (vtable `+0xB8`).
Kind 2 = story flag table digest (host -> client every 2 s): `u8 first dword, u8 count (64), dwords`; the client sets the bits that rose since the last digest and are still clear here (late join, lost events).

## Stage 10: object sync (co-op shutters and pair co-op, movable set models, high flags)

Static findings (Ghidra on the 2019 build, details in the private notes): the co-op classes `uSmDoorCoop`, `uSmShutterCoop` and `uSmPairCoop` share one action scheme (vtable `+0x138` table, `+0x13C` count 7): 0 Closed / Wait, 1 SyncPostion, 2 LoadWait, 3 Opening (the door also 4 NpcAction), so a human's press is the change 0 -> 1 for each of them and the press replay of 6f applies to all three. Their stock press handler `FUN_0074F9E0(set model, slot)` (the action-button callback that `vf +0x1EC` registers) writes `+0x4230[slot] = 1`, calls the virtual `+0x1F4` (the shutter resets its opening side `+0x43C4` there) and then `Act` (`+0x170`); the replay does those two steps too for shutters and pair co-op models (`net w doors coop 2`, the default; `3` does them for the door as well, whose proven call stays Act only). The partner check (`FUN_007548A0`, run by the SyncPostion start) refuses while the set model's `mAccessType` (`+0x43A4`) is 1, which the FSM's `SmCoopAccess(1)` writes on one PC only when its presence tests differ: the replay holds it at 0 until the copy left its waiting action (2 s at most), then writes back the FSM's value (`sSetModel +0x2B0`); `net w doors access 0` switches that off. A replayed press that did not take (still waiting after 0.5 s) is logged.

Movable set models: push boxes `uSmPress` (101 and 151 `uSm1805`: actions 0 Wait, 1..4 Press with a direction) and carried objects `uSmInteractive` (holdable boxes `uSm1160`, bricks `uSm1814` / `uSm1928`: 0 Wait, 1 Pickup, 2 / 3 / 5 Break, 4 Broken). Their box checkers (`uSmMoveBoxPosChecker`) test the box's root matrix against their zone and set a stage flag or an EpisodeFlag (`99000 + n`); the FSM's `AreaHit` on a box (154) reads the box position too. PROP carries the transform from the PC whose human pushes / carries, so the other PC's FSM `AreaHit` on the box (the 154 holes) sees the box itself. A checker's flag reaches the other PC by the flag mirror (SF / EpisodeFlag event): the stock checker `FUN_007D7BB0` sets its flag only when the box comes to rest in its zone after a player of ITS OWN PC moved it, and the flag only latches (`FUN_007D88A0` never clears it); pair run wpB4: the carrier's PC `SF[47] 0 -> 1` at the put-down, the partner `SF[47] = 1 applied from the other PC` 12 ms later, before the final rest.

Scenario flags are read as the game's bit words (`FUN_00975B50`, thiscall on story `+0x31320`): 16 words for the current area (flags 0..511) and 16 for the EpisodeFlags, one call each per scan. At the end of the quiet window after a level load one digest per kind goes out (`0x12F`).
Console: `net w props [on|off|list]`, `net w doors access 0|1`, `net w sf ep 0|1`, `net w sf digest 0|1`, `net w sf check` (the word reader against the game's getter for all 512 flags and the EpisodeFlags). Logic and tests: `native/objsync_logic.h`, `tests/test_objsync.c` (built with `-DOS_MODEL_RELEASE020` the same checks fail: they describe what the earlier code did not do).

Shown on the pair (two copies on one PC, 2026-11-07, build rev2-int): the word reader agrees with the game's getter on both PCs in stages 100, 101, 151 and 153; the press replay of a co-op shutter in both directions (Claire's `(100,161,2)` from the host, the border shutter `(100,161,160)` from the client, Barry's `(153,160,0)` from the host): the other PC runs the whole chain and both humans end beyond the shutter, the stage change follows on both. Two faults found there and fixed: the replay's own change 0 -> 1 was often sent back (at the scan the action instance did not carry the puppet as its actor yet; only the partner's busy guard ignored it): a co-op change to 1 within 2 s of a replay on that set model is now never sent unless this PC's human is the actor; and the digest after a stage change was dropped because the baseline is taken while the session is loading: it now waits until the session plays (`SF digest sent ... area 151` / `101` after the barrier). Not shown: movable objects (no push / pickup reached), the slides and pair co-op boosts, stage 152 / 154.

## Real AI enemies (6c)

The host's enemy AI is the truth: it chooses the human to chase (a type-2 puppet is a valid target), starts the attacks and takes the damage. The client's replica follows the records (position, action, HP, target slot); with `net w ai 0` (default on a client) the replica's own AI update (the enemy's `Intel`, a task of the game's job runner, entry `0x600F50`) returns at once, so only the host's decisions act.
Coverage of the AI switch (read from the code, 6d): the update of every `uEm*Intel` class ends in the common `0x600F50`: the classes with an own `vf46` either jump to it (Em1300, Em5000, 5001, 5010, 5400: `cmp [ecx+0x30],0; jne 0x600F50`) or call it first and add timers and effects (Em0100 / 0200 / 0300: two countdown floats and a state-change effect; Em1500: starts a queued action id; Em3000: clears a flag first). Only `uEm3500Intel_vf46` (0x4FF4E0) runs further per-interval logic of its own (four sub-steps) after the common update; replicas of that class keep it.
Enemy attacks on the human of the other PC are not forwarded (`pdmg` stays off): the replica plays the attack action it received and the game's own attack collision hurts the real body on that PC (measured on the pair: exact, one bite = one damage, the host's puppet gets the owner's HP back through STATE).
A kill the client's human makes: HIT (client -> host), the host applies it with the puppet as attacker, DEATH (host -> client, killer slot + blow flags), the client's replica dies through its ApplyDamage with the client's human as attacker, so the game's own kill evaluators (`Result_OnEnemyKilled_A/B`) credit that human on that PC.

### Kill credit and the profile (6d, measured on the pair)

The game's kill report `FUN_00986230(story, enemy, DamageInfo, max hp)` (prologue `83 EC 10 53 56`, `ret 0xC`) calls `Result_OnEnemyKilled_A` (kind by the killer's blow / weapon: knife `0x26`, melee `0x28`, grapple `0x2A`, bar weapons `0x33`, stone `0x35`) and `_B` (kind by the enemy class). Each kind goes into three tables of the profile (the story block): the global total by kind (`story+0x1DC`, u32 x 0x51, **this is what the achievement records compare with their goal**), the per-slot table (`story+0x1403F8`, u16, 0x66 per slot) and, only when the killer slot is a human on this PC, the credited ledger (`story+0x14A058`, u16 x 0x51). The counter functions are thiscalls on `story+0x31320` (global: `story+0x20`).
On the client the report would not run for a replica that dies by a synthetic damage (the real path stops when `enemy+0x39D8` is set or `+0x37B8 < 0`, and a DEATH replay carries no DamageInfo), so the client calls the report itself before the lethal ApplyDamage when the DEATH names the local human. Measured: `kill reports` 1 per client kill, the client's tables rise (knife `0x26`, crow kinds `0x1A`, `0x47`), the host's tables do not move.
The global total is bumped for any killer slot, so a **stat guard** (`net w statguard 0|1`, default on in a session) runs every report on a snapshot of the three tables and rolls it back unless the killer is the local human (on the host only the remote puppet's kills are rolled back): a partner's kill never moves this profile's achievements. `net w stats [ach]` prints the tables, the guard counters and, with `ach`, state bits / goal / total of the kill records; `net w killrep <a> <b> <c> <slot>` runs the report for a live enemy with that slot's player as the killer (test of the guard).


## The puppet's equipment

The STATE message carries the item ids of the weapon slots 1..3 and the slot in the hand. The receiving PC finds each item in the puppet slot's personal inventory (`sInventory[0x157D3F4] +0x418`, entries `+4` id, `+0xC` count) and equips it with
`FUN_00710360(player, inventory index, slot type, equip now)`, the call the game's own Raid receiver makes. An item the puppet's inventory does not hold is not equipped (counted as "item missing"); the inventory is filled by the story itself and by PICKUP / GRANT.
Action ids the puppet may play: a 256-bit mask, `net anim add <id> ...`; the learning table logs every id the local human produces (`action id N first seen`).

## 6e: the story scripts, scenario flags, door operations (research tools)

The story is data: the stage archives hold the scenario FSMs (`soft/stage/sNNNN/fsm/*`, an `XFS` serialisation of `cAIFSM` objects: nodes, transitions, `cAIFSMNodeProcess` orders such as `Door`, `Flag`, `SmSet`, `EnemySet`) and the trigger zones (`sNNNN_flag`). The FSMs read and write **scenario flags** (SF, bit arrays per stage in the story block; read `FUN_00A90510(index)`, set `FUN_00A91AE0`, clear `FUN_00A91A60`). Every PC runs the same scripts, so most flags agree by themselves; what only one PC sees (its own human entering a trigger zone) sets flags on that PC only.

- `net w sf` lists the set flags of the current area, `net w sf get <n>`, `net w sf set <n> <0|1>`, `net w sf watch 1` logs every change (`SF[n] a -> b`), `net w sf sync 0|1|2` sends flag changes to the other PC (`SF` event `0x12C`: `i32 area`, `u16 index`, `u8 value`; 1 = sets only, 2 = clears too; the receiver applies through the game's setter and takes the value as its baseline, a level (re)load restarts the baseline). Off by default.

## 6g: the engine's game-over state, holds (2026-11-04)

**Deaths are read from the engine, not guessed.** The game keeps a state machine in the area object (state byte at `aGame+4`; 3 = gameplay, 9 = scenes, 0x0B = game over, the state that builds the death screen) and, once per gameplay pass, tests every human slot with one predicate: hp < 1, bit 1 of the controller word (`player+0x78E8`), bit 14 of the state word (`player+0x37B8`) or bit 28 of `player+0x7904`; a hit marks the slot in a dead mask (`sGameMan+0x878`) and enters state 0x0B. The glue sends `DEAD` when the mask bit, the game-over state or (in gameplay only) the predicate says so, plus the old shapes. Shown on the pair: a human held by an enemy dying with hp above 0 (pstate 4000), a fall into the void (controller word 00001002) and the same on the host; the partner died within 0.5 s each time and the coupled retry reloaded both PCs three times. **Holds.** A hold by an Afflicted lasts about 5 s by the engine's own timer (the break-free input bits rise at fixed times whether or not the stick moves). The human's grab action releases itself (`ChangeAction 0xB9`) when the holder's action leaves the grab chain (0x4D..0x58). ## ep1-cover: the checkpoint, the coupled Retry, the lab warp (2026-11-07)

**Where a checkpoint lives.** The game data of a run is cGameInfo = story block + 0x31320 (mTempData.mBase: mStageNo +0x10F060, mStartPosIdx +0x10F064, mSceNo +0x10F068;
per-stage scenario flags +0x123740, 20 slots of {stage id, 16 words}). The game area owns a second cGameInfo, the restart copy `[aGame + 0x608]`, filled by every CHP scenario

## 0.2.0 MHIT: the client's real blows on replicas (2026-11-07)
Every real blow on an enemy (knife, kick, stomp, bullet, thrown object) is stored by the collision code in the enemy's pending DamageInfo (enemy+0x30E0, valid byte +0x31B0; body parts: the 10 part objects at enemy+0x7328 with their own DI). The only code that turns it into damage is the enemy's Intel update (`uEmIntel_vf46` 0x600F50 -> FUN_006001D0 -> the hit handler FUN_0061B050: damage formula, reaction, ApplyDamage, kill report). With the replica AI off a client skips that update, so before MHIT a client's blow on a replica did nothing (34 knife slashes, 0 ApplyDamage, run G1).
Now the skipped update of a replica reads the pending DI and, when the attacker is the local human (or an object it owns), sends it to the host as event `0x130` HITDI (the field list of the game's own Raid compact pair). The host queues it and, in its enemy's Intel update (before the stock part), hands the rebuilt DI (attacker = the partner's puppet) to the hit handler directly, the way the game's Raid receiver does (FUN_0061B050 + FUN_00ADD880): damage formula, death, kill report (DEATH gives the kill to the client's human); the stock update right after picks the reaction. Posting it into the enemy's pending DI instead does not work: the stock check FUN_0060DFD0 refuses a DI whose attacker is a network-type player (type 2, FUN_009F3B10) when enemy+0x6FB8 is set (run M1: 5 posted, 0 damage). A blow no update takes in 1 s is applied from the game pass. The replica changes nothing locally (the host's records show the reaction); the partner's puppet's DIs on a replica are ignored. Switch: `net w mhit 0|1` (default on), `REV2_MHIT=0`. Offline: `tests/test_meleehit.c`.

## combat4: the partner's inventory copy, the partner's throw, the puppet's hand (2026-11-08)
**Inventories.** Every PC holds a copy of the partner's personal inventory (`sInventory [0x157D3F4] +0x418`, 34 entries: id `+4`, count `+0xC`, a gun's loaded rounds are its count) and writes it into its own checkpoint save together with its own human's. Before combat4 only pickups (`PICKUP`) and unique grants (`GRANT`) crossed, so nothing the partner consumed (a thrown bottle, rounds, a herb, a used key, crafting) left the copy: the host's copy of a client's Moira went `0147 x1 -> x2` after two pickups and two throws. Now each PC is authoritative over its own human's inventory: it sends the changed entries (event `0x131` INV: slot, flags, n x {index, id, count, +0x18}) and a full set on request (`0x132`, asked every 2 s until the table is complete, and after every level load: a retry restores each PC's own save), and the other PC reconciles its copy every 250 ms (counts written, missing items put with PutItem, empty stacks removed with the game's own remove `FUN_00993BC0`, the last throwable with the stock consume `FUN_007151A0`; weapons are never removed). An id this PC itself put into the partner's copy (its own story grant, a PICKUP / GRANT replay) is left alone for 3 s. Console: `net w invm [0|1|log n|full]`, `REV2_INVMIRROR=0`.
**The hand-over.** The campaign inventory screen (`uGUIInventoryCampaign`, update `0x8FA590`) shows both humans' grids and moves items between them (the walkthrough's "give the bottles to Moira": `FUN_009938F0` + `FUN_00993BC0`). A difference this PC's screen made to the partner's copy is sent to its owner (`0x133` INVADJ: id, delta) and applied there to the real items. (flashlive, 2026-11-09) The real screen's pass (T, the cursor, C = PassItem) runs in a state handler outside that vfunc (pair run flashlive-a: two calls for a whole open / pass / close, the bottle vanished: the mirror took the copy's +1 back). A per-frame watcher (`invmirror_logic.h` `im_pass_delta`, `story.inc` `im_pw_tick`, before the reconcile, the copy re-read after it) now takes an id that left this PC's human and arrived in its copy of the partner in the same frame (or the reverse) as a hand-over and sends the INVADJ; shown live in run flashlive-b (`INV hand-over in my inventory screen (pass watcher) ... 0147 +1`, the owner `... applied to my human (slot 1): item 0147 +1: 0 -> 1`).
**The partner's throw.** A type-2 puppet stops the stock throw before the launch (`player vtable +0xE0`), so the other PC never saw the partner's bottle fly or explode. The thrower's PC now sends the launch vectors of its human's projectile (hook on the Raid sender `FUN_009F7C70`, event `0x134` THROW) and the other PC creates the same `uWpBomb` for the puppet the way the game's Raid receiver (`FUN_009DF640`) does; its owner (`+0x19C0`) is the puppet, so the host drops its own hit on the host's enemies (combat2 P2) and the damage comes once, as MHIT from the client. Console `net w throw [0|1]`, `REV2_THROW=0`.
**The puppet's hand.** It followed the owner's weapon slots 1..3 only and was never cleared: after a throw the puppet kept the bottle in its hand. Now an empty owner's hand gives the puppet its default item (`FUN_00710360(p, -1, 0, 1)`) and the owner's light (hand slot 4) gives the puppet its light.
**Follow-up.** The battery of Moira's light is its entry count and changes every 100 ms while she shines: a battery-only change of less than 20 is sent at most once a second (any other change at once). Moira's flash is a hit: the light's DI carries flag bit 26 (DI+0x28), the hit handler ORs it into the enemy's hit record (+0x38DC) and uEm1100Intel_vf62 picks DmgFlash (act 162) from it; a client Moira's flash reaches the host through MHIT like any blow (damage 0 is not filtered). Log lines for a session: the host `flash stun on the host: enemy (a,b,c) ... act 162 (DmgFlash) ...` and `flash-stunned enemy (a,b,c): act ...`, the client `flash stun: replica (a,b,c) ... shows the host's act 162`.

## bomb: one damage path for the partner's thrown bomb (2026-11-09, notes\bomb.md)
**What the game does.** The bomb's flight update (`uWpBomb_vf134` `0x673CA0`) starts the impact explosion of a throwable (action 8 on the bomb's action controller at `+0x1A38`) only when its owner (`+0x19C0`) is a LOCAL player (`FUN_00673000`: owner vtable `+0xE0`), then calls the Raid sender `FUN_009F6EF0(owner, bomb)` (message 0x21: the bomb's net id, item id, position). The Raid receiver `FUN_009E07E0` puts the remote copy at that position and starts the same action 8. The copy THROW creates for the puppet has a type-2 owner, so it never exploded: the damage of a partner's bottle always came from the thrower's real explosion (MHIT from the client's replicas, the stock hit on the host). Flashlive's "no MHIT, no puppet blow dropped" was the log cap: 60 MHIT lines per PC were used up by the light's damage-0 hits 11 minutes before the throw.
**The path.** The thrower's real explosion deals the damage. The thrower's PC hooks `FUN_009F6EF0` and sends `0x135` BOOM (throw number from THROW, the explosion point); the other PC finds its copy of that throw (a live object in sItem's list), moves it there and starts its explosion: the partner's bottle now explodes on both screens (and its noise wakes the enemies of that PC as the stock one does). Every blow of a copy on the host's enemies is dropped before the stock update reads it: the explosion's DamageInfo names the bomb's owner as attacker (live, run a2: the puppet for the copy), so P2's `attacker == puppet` rule drops it; a table of the copies drops a DI that names the copy object itself; on the client a copy's blow is never MHIT (its attacker is the client's puppet of the thrower). One explosion = one MHIT per hit replica (live: damage 1224 / 1200 / 1440, hp on the host 3000 -> 1776 / 3000 -> 1800 / 600 -> 0 once each). Console `net w throw boom 0|1`, `REV2_BOOM=0`.
**Kill credit.** A bottle's kill comes with the thrower as attacker (MHIT: the puppet -> DEATH killer slot = the client). A weapon object as the attacker (not seen for bottles) counts for its owner (`+0x19C0`). A burn tick (the hit handler keeps the attacker of a burning blow, DI+0x28 bit 24, at enemy `+0x7378`; `FUN_0061AC70` then runs the hit handler with a new DI per tick: attacker 0, DI+0x2C bit 27) counts for that igniter: a kill by the burn of a client's bottle is the client's (DEATH killer slot), and the host's stat guard rolls it back on the host.
**One blow per update.** The stock reader `FUN_006001D0` applies ONE of the enemy's and its part objects' DIs per update (the one with the most damage); the client now sends only that one as MHIT (several DIs of one explosion on one enemy were several MHIT).
**Logs.** MHIT lines have separate budgets for damage-0 hits, hits with damage and blows of an object; `THROW sent/applied ... (throw N)`, `BOOM sent: my thrown 0147 (object X, throw N) explodes at (...)`, `BOOM applied: the partner's (slot N) 0147 copy X (throw N) explodes at (...)`; the copy's blows appear as `puppet blow dropped on the host: ...`.
